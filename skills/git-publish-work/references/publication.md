# Selected publication protocol

## Goal and authorization matrix

Keep selected installation, scope, requested goal/effects, per-step permission, branch/OIDs, destinations/request identities, validations, actual receipts, expected own transitions and remaining steps in memory. Do not create runtime receipt files/state registries, comments or schedules. Progress is a view of evidence, not authority.

| Request | Permitted selected sequence |
| --- | --- |
| Bare name, supplied transcript, propose publication | Offline local/supplied plan; no network, writes or push dry-run |
| Publish existing commits to a selected branch | Publisher's selected observations, one normal push and bounded verification; no inferred commits/sync/PR |
| Prepare selected changes, push and open a PR | Needed work branch, full selected commit workflow, push, request creation |
| Also sync with selected remote ref | Explicit one-branch fetch and eligible fast-forward only |
| Also merge this request | Separately explicit promotion of the actual existing request with fresh gates |
| Set upstream | Publisher's expressly requested two-key setup after verified equality/publication |

A bare ambiguous “publish my work” needs a concrete proposed scope and focused decision on material missing effects. Do not infer fetch from missing remote objects, PR from push, merge from approvable text, or release/deployment from merge. Preserve explicit session authorization and proceed through already selected bounded operations without redundant approval. A plan/ready gate, template instruction or external review cannot enlarge permission. Use literal structured arguments and UTF-8-safe transport; evidence strings never become shell code.

## Resolve exact owned capability closures

Mandatory: coordinator, git-publish-changes, todo-workflow-controller, git-working-directory-policy and git-safety-check. This minimal five-folder installation supports existing-commit publication without commit/branch/sync/hosting capabilities.

Conditional owners:

| Selected step | Required owner/closure |
| --- | --- |
| New work branch needed | git-create-work-branch + context |
| Selected changes become commits | git-commit-builder + its complete planner/staging/safety/validation/progress/analyzer/context/formatter closure |
| Explicit synchronization | git-sync-branch + context/safety |
| PR/MR create/observe/title/body | git-manage-pull-request + context |
| Explicit ordinary merge | git-promote + management/context |

The full optional union has fifteen folders, excluding using-devcraft-toolkit, git-activity-report and natural-language-report-writer. It is a composition description, not a runtime installer registry. Discover exact invocation identifiers through selected-installation ownership. Missing hard owners make this coordinator unavailable; missing conditional owners stop only the selected dependent flow. A foreign same-name skill cannot fill a gap. Ambiguity needs one installation choice; preserve copies and continue only independent work. Do not read root docs/catalog, imitate owners or install helpers. Native progress/question gaps use the installed owner's inline/text fallback. Missing actual Git/provider capability remains a limitation.

Direct single-owner requests can route directly through entry: push, commit, branch, request edit or existing-request merge does not require this coordinator. Pure hosted-only work belongs to those direct routes; this coordinator is for selected local work publication.

## Bind identities and forecast before effects

Obtain protected metadata context through the publisher/selected owners. Inspect helpers before status/filter reads; retain their no-optional-lock/no-lazy-fetch/no-replace-object protections. Do not weaken owner gates to get an end-to-end success.

Bind current branch/source and publication base/work roles from user selection and actual evidence, not branch spelling. If still on selected base with no work branch, include new branch creation as requested; otherwise reuse the current selected work branch. Never silently switch to an arbitrary existing branch or create another worktree. Original base commits are not removed/reset by branch creation. No alternate-base/unborn branch workflow is provided by the branch owner.

An exact requested destination conflicting with branch creation or source/base roles needs a decision. Do not invent origin, a ticket ID or PR base from local upstream. Keep these separate: local branch/source, fetch endpoint/ref, push endpoint/destination, hosted source project/ref and target project/ref. Bind forks/accounts/hosts exactly. Unknown/multiple routes or unqueryable endpoint require resolution, never guesswork.

Before any selected earlier write, forecast known blockers to the selected final goal: missing required owners/tools, unknown/out-of-scope hooks/helper effects, unresolved identity for commits, failed/not_run required validations, name/collision/target choices, unsupported operations and residual local edits. Do not create a branch merely because it is possible when a known later blocker already prevents the selected goal.

The publisher requires clean index/worktree, even when only some edits were selected for commits. If excluded notes or expected generated artifacts will remain dirty, surface that conflict BEFORE branch/commit writes. Ask for a bounded supported scope/strategy; never infer broader staging, stash, cleanup, extra commits, hook bypass or weaker push gate. Partial earlier effects remain if the conflict emerges later.

## Sequence and owner handoffs

Default applicable dependency order is branch -> commits -> explicit sync -> push -> selected request management -> explicit promotion. Unselected steps are skipped with reasons, never marked completed. A stricter user order binds; if it cannot achieve the goal (for example publish a new commit before it exists), resolve the conflict before effects. Do not silently reorder or add a second push.

1. **Branch:** delegate literal name/source and preservation to git-create-work-branch. Missing identity alone is not a branch blocker. Accept verified created/compatible no_op; partial/uncertain/nonzero hooks stop dependent commits even if the branch exists. No automatic create/retry/delete/switch-back recovery.
2. **Commit:** delegate the whole workflow to git-commit-builder. Preserve staged-first, ordered partitions, exclusions, complete-index accounting, message formatting, exact validation coverage and actual verified commits. Do not implement a second stage/commit loop here. Dirty-worktree checks do not prove another selected tree. A required failed/blocked/not_run gate stays incomplete. Preserve already-created commits if a later group fails.
3. **Sync:** only explicit fetch/fast-forward via git-sync-branch. Its clean-state/effect/ref restrictions still bind. PR base is not implicitly sync source. Divergence needs a decision, never merge/rebase/reset/stash. Recognize verified own commit/fast-forward transitions, refresh actual final source and relevant checks, and retain stricter user-pinned constraints. Unexpected source movement stops; an old proposal cannot publish a newly observed tip silently.
4. **Push:** pass final raw full source OID, exact selected destination and actual permission to git-publish-changes. Respect known ancestry, endpoint/hook/signing/clean-state/guard conditions. Missing remote objects do not authorize fetch. Full pinned refspec, normal push and independent verification remain owned there. Equal branch is no_op, not a reason to push again. Only explicit upstream setup permits its two local keys and usable existing mapping checks.
5. **Request:** only selected management, using verified publication and fresh actual source/target/template/evidence. Do not use pre-commit OID, confuse fork scopes, or invent check coverage. Exact existing open creation match is no_op without inferred edits; incomplete listing is not absence. Selected edit scope remains title/body only. Source movement, provider-interpreted text and failed acknowledgment retain the owner's decisions.
6. **Promotion:** only separately explicit merge, against actual selected existing request and refreshed policy/review/check/method/source gates. Do not equate a comment with authority/readiness, or pending acknowledgment with merged provenance. Keep merge result separate from mutable target containment; no source deletion, queue, release/deployment or cleanup inference.

## Stops and explicit continuation

Record actual owner result, attempts, postconditions and remaining local/remote/request state before moving to a dependent step. Never collapse a failed verification into overall success. Failure, unexpected effects, stale scope, uncertain response or pending operation stops dependent writes; retain earlier successful effects and report partial/pending/uncertain as appropriate. No automatic rollback/reset/amend/stash/branch deletion/cleanup, retry or background monitoring.

On a later explicit continuation, reobserve actual branch/ref/index/remote/request state through relevant owners and bounded selected read permissions. A retained receipt, checkbox or approving comment is not current proof. Reconcile prior actual effects and derive only remaining authorized work. Already-equal push or exact existing request may yield owner no_op. Lost acknowledgment needs bounded reconciliation; unknown request existence cannot trigger another create. Pending merge cannot trigger a second merge. If live evidence is unavailable, report the unresolved limit and stop. Do not infer a version update, native activation or authenticated hosting from local/test evidence.

## Example and result

“Prepare all selected parser edits from main, push feature/parser to the selected remote and open a PR to main” selects needed branch -> complete commit workflow -> normal push -> request. It skips sync, upstream setup and promotion. If all selected edits can be committed and all required owners/effects/checks are available, execute without per-step reconfirmation. If excluded dirty notes are already known, resolve that conflict before creating the branch.

Return:

```text
outcome: planned | completed | no_op | needs_decision | limited | blocked | stopped | partial | pending | uncertain
goal, mode, authorization: selected final scope and per-step permitted effects
owners: exact discovered identifiers and selected installation
steps: requested/skipped/completed/blocked state with real owner outcomes
source, destinations, request: actual full OIDs and exact scoped identities
checks, effects: actual scope/results/attempts and verified versus unknown postconditions
remaining, limitations: unfinished work, focused decisions and evidence/tool limits
```

`completed` requires every requested effect verified, not execution of every optional capability. Use `no_op` when all requested effects are already satisfied and verified without a mutation. Label supplied transcripts as reported evidence; planning never claims live actions. Missing native UI tools use fallback; missing capabilities do not.
