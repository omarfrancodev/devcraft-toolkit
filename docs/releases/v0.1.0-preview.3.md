# Devcraft Toolkit v0.1.0-preview.3

Experimental read-only Git preparation, prepared in PR #5 with its changelog and release documentation in the same merge. The GitHub release tag must target that merge commit; no follow-up release-preparation commit on main is required.

Nine skills are available and eight catalog capabilities remain planned. Native plugins/Powers and complete skill sets expose the same canonical resources; delivery, scope and lifecycle differ by client. Crew uses its own importer and existing agent, without a toolkit template or App.

See the [changelog](../../CHANGELOG.md), [installation overview](../installation.md) and [compatibility evidence](../compatibility.md).

## Included capabilities

`git-analyze-changes` adds local layer-specific evidence, bounded content coverage and HEAD/index/content guards. `git-plan-commits` proposes intent groups and messages through the existing formatter. It narrows requested paths before choosing explicit layers or applying staged-first within that scope.

Both capabilities are read-only. Staging, commit execution, branch creation, validation execution and publication are not part of their runtime contracts. A configured external clean/process filter selects a conservative limited worktree fallback.

The complete suite includes the seven earlier capabilities plus these two skills; selected installations need their explicit dependency closures. Earlier preview.2 remains a seven-skill snapshot.

## Downloads and integrity

Download `devcraft-toolkit-v0.1.0-preview.3.zip` and `SHA256SUMS.txt` from [the GitHub release](https://github.com/omarfrancodev/devcraft-toolkit/releases/tag/v0.1.0-preview.3).
Verify the ZIP's SHA-256 against that file before extraction. The ZIP is a source/package archive of the exact tagged merge commit, including canonical skills, manifests, docs and external tests. It excludes Git internals, ignored worktrees, caches, temporary files and generated distributions.

PowerShell `Get-FileHash -Algorithm SHA256` or a platform's `sha256sum` can calculate the download digest. Consumers normally use remote installation routes; manual copies must include complete skill folders and every required dependency.

## Validation boundaries

Implementation verification discovered 89 tests: 88 passed and one existing Windows symlink privilege case was skipped. Repository/distribution validators and the complete branch whitespace check passed. The [retained verification](../../tests/integration/evaluations/2026-10-24-git-preparation/final.md) describes the implementation snapshot before this release preparation.

Fresh supplied-fact controls/candidate samples and real disposable Git recipes are separate evidence. They do not establish native discovery or authenticated invocation of the new skills. A targeted path-only planning probe reproduced the layer-selection ambiguity and its correction; staging outside requested paths does not suppress the in-scope fallback.

Prior Codex/Claude/Copilot remote probes establish only their recorded versions, revisions and narrower acquisition/resource observations. They precede the root activation-keywords correction and do not prove this release's native loading. Kiro metadata follows the documented keywords requirement, but actual IDE/CLI activation remains pending.

Authenticated invocation, model-driven resource reads, active project/control isolation, repository auto-install, VS Code crossover, Crew trust/agent sessions, and version-changing cross-scope lifecycle remain open where recorded. Project-only native Kiro Power is `not_supported`; the project skill-set route is separate. The installation plan's Task 4 Step 3 stays open. This is a prerelease, not stable or complete seven-client compatibility.

## Publication procedure

Prepare the versioned changelog, both manifest versions and these consumer docs on the PR branch. Verify the tree, then merge PR #5 with an expected-head guard. Build the ZIP from that exact merge revision, verify its entries against Git blobs, run package checks and publish the prerelease tag/assets at that same revision. Keep previous release assets and tags unchanged. No automatic installer, release workflow, license or marketplace submission is introduced.
